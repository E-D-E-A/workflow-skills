Editing questionnaires from chat

The survey tools let you build and change a questionnaire by describing the change in plain words. Nothing is written until you have seen the diff and said yes.

The shape

Three things, and the difference between them matters more than anything else on this page.

ThingWhat it is
SurveyOne questionnaire. Has a short slug the tools use, and a Hebrew name people read.
DraftThe working copy. Everything on this page edits the draft. Respondents never see it.
Published versionWhat respondents actually answer. Created only by a person, in the admin console.

Editing the draft is not publishing. A change you apply here sits in the draft until someone opens the console and publishes it. If a change has not shown up for respondents, this is almost always why.

The seven tools

You never call these by name — you describe what you want. They are listed so you can recognise what happened.

ToolDoesWrites?
list_surveysEvery survey: slug, Hebrew name, whether a draft exists, how many versions were published.No
get_draftThe current draft as a Hebrew outline — screens in order, routing and conditions written as sentences.No
propose_changeA dry run. Validates the change and returns the diff for you to read.No
apply_changeApplies exactly the change you approved, to the draft.Yes
simulate_pathWalks a set of answers through the questionnaire and returns the exact screens that respondent would see.No
create_surveyA new survey and an empty skeleton draft.Yes, at once
get_audit_logRecent changes made this way: who, when, which survey, what changed.No

How a change goes in

Always this order. The review step is the point of the whole thing.

The route every change takes

say what you want → it loads the draft → it proposes → you read the diff and say yes → it applies → it simulates the paths

  1. Say what you want changed

    Plain words are enough — "add a question after the income screen asking how many dependants they have, and skip it for renters".

  2. Answer the questions it asks back

    It stops and asks when something was implied rather than said — a threshold, the exact Hebrew wording, where a screen sits. Answering these is faster than fixing a guess.

  3. Read the diff

    You get the before and after, plus whether the change is valid. Nothing has been written at this point. If it is not what you meant, say so and it proposes again.

  4. Say yes

    Only now does anything change, and only in the draft. Saying nothing is not saying yes — the change simply waits.

  5. Check the simulated paths

    It walks the affected personas through and shows the screens each would see. A change can be valid and still route someone somewhere nobody intended; this is where that shows up.

  6. Publish it yourself, in the console

    Review the draft in the admin console and publish it there. Until you do, no respondent sees any of it.

What it will not do

Not restrictions that can be lifted by asking — there is no tool for these at all.

  • Publish a survey. A person does this in the console, on purpose.
  • Archive, rename or delete a survey. Console only.
  • Touch a published version. Every write goes to the draft.
  • Change analysis codes once a survey has been published. Answers already collected point at those codes, so they are frozen. You get an explicit rejection.

Two things that trip people up

  • Creating a survey happens immediately. Unlike every edit, there is no dry run and no undo for create_survey. Check the slug and Hebrew name before you say yes.
  • Someone else may be editing. If a person saves in the console while you work, your change is refused rather than merged. It reloads and proposes again — read the new diff, because it may no longer say what you intended.

Signing in

Your own account, every time. There is no shared login anywhere in this.

The first time you use a survey tool, a browser window opens and asks you to sign in with Google. Use your work account. The session is cached on your own machine, so you do this once and then rarely again.

  • Signed in with the wrong account, you get a refusal that says so — sign out and retry.
  • Every change is recorded against the account that made it, and shows up in the change log.
  • Nothing about your sign-in is stored in the plugin or shared with anyone else.

Install

Once per person, per machine. Needs Node 20 or newer.

Install once

/plugin marketplace add E-D-E-A/workflow-skills
/plugin install edea-mortgage-survey@edea

Then restart Claude Code. On the first survey request, the Google sign-in window opens.

The skill you get

SkillFires when you
survey-editAsk to add, reword, reorder or remove a question or screen, change routing, conditions, quotas or draws, start a new questionnaire, or ask what a respondent would see.

Updates

Turn on auto-update: /plugin → Marketplaces → enable it. Without that you stay on whatever version you first installed, quietly, while everyone else moves on.

Not finished yet

This plugin ships the survey tools and one skill. It does not yet write changes back to Linear or Confluence for you — the skill reminds you, but you do that part by hand.

The skills tell Claude how to work; this page tells people how to work. If they ever disagree, the skill is what is actually running — say so and it gets fixed.
