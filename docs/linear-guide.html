Working in Linear

Which team an issue goes to, what each status means, which label to use, and how to write one somebody else can pick up.

Two teams, permanently

Teams are how work gets done. Projects are what we're building. A new venture is a new Project — never a new team.

Next thing to do is write code → Engineering.
Next thing to do is talk to a person → Business.

ENG

Engineering

Everything that ships. Runs in fixed cycles.

  • Features and bugs
  • Cleanups and refactors
  • Releases, servers, setup
  • Throwaway coding tests
  • Developer tooling

BIZ

Business

Decides what to build and who pays. No cycles.

  • Customers and validation
  • Pricing and partnerships
  • Legal, fundraising, finance
  • Product and design calls
  • Operations and admin

When it looks like both

Split it. A coding test to see if an outside service works is ENG; deciding whether a customer will pay is BIZ. One issue, one team — when business work leads to building, open a linked ENG issue rather than moving the original.

Statuses

Each team has its own. They say where the work is, not how far along it feels.

Engineering

Backlog→ Todo→ In Progress→ In Review→ Done/Canceled

Business

Backlog→ Todo→ In Progress⇄ Waiting→ Done/Canceled
BacklogNot shaped yet, or maybe-someday. Leave unassigned.
TodoDecided and queued. On BIZ this is the "what's next" list.
In ProgressSomeone is on it right now.
In Review ENGPull request open. GitHub moves this for you.
Waiting BIZBlocked on someone else — investor, lawyer, customer, teammate.
DoneShipped, decided, signed, produced.
CanceledDropped or died. A lost deal is Canceled, not Done.

Why Waiting exists

It answers the only question the board needs to answer: what needs me, versus what am I blocked on.

  • Keeps In Progress honest — parked work stops looking active.
  • Makes idle time normal. Two weeks on an investor isn't neglect.
  • Doubles as the follow-up list: Waiting + untouched for a week.

When you move something here, make sure Next action says what unblocks it and who resumes.

Labels

One label, for the type of work. Unsure? Leave it off rather than guess. Never stack several to hedge.

Business

productSpecs, roadmap, what to build
designUI, UX, wireframes, prototypes
researchCompetitors, market, regulation, discovery
fundraisingInvestors, pitch, grants
financeRunway, bookkeeping, invoicing, payroll
legalIncorporation, contracts, compliance
opsTools, hiring, suppliers, admin

Engineering

BugSomething's broken — use the bug format
FeatureNew capability
ImprovementMaking something existing better

No label for market or industry — the Project already says which venture. Setup work often fits none of these; unlabelled is fine.

Every label belongs to one team. The seven above belong to Business, the three to Engineering — Linear only offers a team's own labels, so you can't put Bug on a Business issue by mistake.

Writing an issue

In this order.

Anyone should be able to open it and start work without asking you what you meant.

That's the bar for how much to write. Simple task, a line or two. Fuzzy or big, more. Read it back as if someone else wrote it — if you'd have to ask a question to start, answer it in the issue.

  1. Team

    Code → ENG. Person → BIZ.

  2. Title

    Verb first, specific. The thing to do, not the topic. Add invoice export to settings · Decide pilot pricing

  3. Status

    Backlog if it's not shaped. Todo if it's decided and queued.

  4. Label

    One, for the type of work.

  5. Description

    Outcome, always — what done actually looks like. ENG: a checklist. BIZ: the decision or thing you'll have in hand.

    Then, whenever they help:

    • Context — why it matters, constraints, decisions already made
    • Next action — the single next step. Essential if it'll sit in Waiting
    • Open questions — what still needed a human answer, phrased as questions for the owner. Deleted when empty
    • Links — pull request, documents, related issues

    Write it plainly, and explain as you go. Short sentences, ordinary words. Whoever picks the issue up may do it weeks later, and two of us aren't developers. So spell out an abbreviation the first time you use it, explain any term or internal shorthand right where it appears, and when you point at a rule or a document, say what it actually says — a reference on its own tells the reader nothing.

    This usually makes an issue shorter. Once you've simply said the thing, the hedging and cross-referencing falls away.

  6. Assignee

    Unassigned in Backlog. From Todo on, whoever owns the next step. Keep it assigned in Waiting — that's who picks it back up.

Bugs use a fixed format

A bug can't be worked without enough to reproduce it:

## Steps to reproduce
1. …

## Expected
what should happen

## Actual
what actually happens

## Environment
browser / OS / version / URL

GitHub & docs

Name things so Linear can see the connection, and it moves issues for you.

GitHub

Linear links a branch or pull request whenever the issue ID appears in it.

  • Branch — eng-123-invoice-export. Linear's Copy git branch name gives the exact format.
  • PR title or description — the ID plus a keyword below.
KeywordOn merge
Fixes · Closes · Resolves
Completes · Implements		 Issue moves to Done. Fixes ENG-123, or Fixes ENG-12, ENG-34.
ref · related to · part of
contributes to · towards		 Links only, doesn't close. For partial work.

Let GitHub move ENG statuses instead of dragging cards.

Documents

Paste the link in the description — Linear previews it — or attach it with a clear title. Same for Confluence, Drive and Figma.

The shared skills

All of this is written up as skills, so Claude creates and updates issues in our format without anyone remembering the rules. Every skill shows you what it's about to write and writes nothing until you say yes.

linear-issueCreates issues in our format. Checks the Confluence Brain first — our company knowledge base — and links the spec or decision that covers the work. Asks about the work before writing — unknowns stay visible under Open questions, and a batch starts with one sample issue for sign-off.
linear-updateMoves, reassigns, relabels, links, closes, deletes. When an issue that implements a spec page finishes, it offers to check the page still matches what was built.

Changes

The two developers maintain them. If something here is wrong, tell one of them — no need to file anything.

Keep in mind

The skills repo is public. It describes how we work, which is fine to share. Never put target markets, customer names, pricing or strategy in it. What you write inside a Linear issue is private.

If the way we work changes, this page and the skills change with it. When they disagree, the skills are what's actually running.
